# Release and community submission

Plugin name: **Recall Check**. Plugin ID and repository name: **recall-check**. Author: **Zhi Fu**.

`manifest.json.author` controls the installed plugin’s author label. It does not require a matching GitHub display name. `authorUrl` is optional and has been omitted until the owner chooses a real profile or website URL. GitHub repository ownership and the Community directory profile are configured separately.

## Prepare the public repository

1. Create a public GitHub repository named `recall-check` under the intended owner account.
2. Add that real repository URL as the local Git remote and push the source branch when ready.
3. Optionally add a real `authorUrl` to `manifest.json` and `repository` metadata to `package.json`.
4. Add real screenshots using [SCREENSHOTS.md](SCREENSHOTS.md). The README works without them and contains no broken image placeholders.
5. Run `npm run verify`; complete the relevant [in-app tests](../TESTING.md).

Keep `README.md`, `LICENSE`, `manifest.json` and `versions.json` at the repository root. Commit `package-lock.json` for reproducible installs. Do not commit `node_modules`, the generated `main.js`, vault configuration, local `data.json` or credentials. Release assets are generated by the workflow rather than stored in the source branch.

## Versioning

For each new release, keep these in sync:

- `manifest.json.version`
- `package.json.version` and the package lockfile
- the new entry in `versions.json`, mapped to the minimum supported Obsidian version
- release notes in `CHANGELOG.md`

The current version is **1.1.1**, requiring Obsidian **1.8.7**. Documentation and author cleanup before the first public release keep that version unchanged.

## Publish a release when ready

This repository includes a dormant GitHub Actions release workflow. It runs only after a matching tag is pushed to GitHub. It installs locked dependencies, verifies the project and tag, then attaches:

```text
main.js
manifest.json
styles.css
```

The tag must exactly match the manifest version, with no `v` prefix:

```sh
npm run verify
git tag 1.1.1
git push origin 1.1.1
```

Run these publishing commands only when ready to publish. The workflow needs GitHub Actions enabled and permission to create releases. Its `GH_TOKEN` comes from GitHub’s built-in job token; no personal access token is stored in this repository.

If publishing manually, run the same verification, create a GitHub release with the exact version tag, and attach the three root build artifacts. The source archive alone is not an installable plugin release.

## Community Plugins directory

Publishing a GitHub repository or release does not automatically list the plugin in Obsidian.

Follow the current [official submission guide](https://docs.obsidian.md/Plugins/Releasing/Submit%20your%20plugin). It currently requires an Obsidian account, a linked GitHub account, a public source repository and an installable release. Submit the real repository through [Obsidian Community](https://community.obsidian.md), then address review feedback before the plugin becomes installable from the directory.

Review the [developer policies](https://docs.obsidian.md/community-directory/developer-policies) and [plugin submission requirements](https://docs.obsidian.md/community-directory/submission-requirements-for-plugins) at submission time. Account sign-in, ownership selection, policy acceptance and the final submission belong to the repository owner.
